OpenClaw vs Hermes Agent: The Full Comparison (2026)

Two MIT-licensed, self-hostable AI agents, two very different CVE records, and different defaults for sandboxing. A docs-based comparison, re-checked in October 2026, for anyone about to run one on their own server.

Short answer: OpenClaw and Hermes Agent are both MIT-licensed agents you host yourself, and both support MCP, sub-agents, a built-in scheduler and 20+ chat platforms. Pick OpenClaw for the widest channel and device reach. Pick Hermes Agent for self-authored skills and a documented eight-layer security model. Neither isolates command execution unless you configure it.

Updated October 2026. I re-read both projects' READMEs and docs as raw files on 2026-10-23 and re-pulled the CVE records from NVD the same day. The first version of this article stated several things the docs contradict; they are corrected below.

If you want an AI agent that runs on hardware you control rather than a hosted product you rent, two projects dominate that lane: OpenClaw, the foundation-governed successor to Clawdbot and Moltbot, and Hermes Agent, Nous Research's self-improving agent. Both are free, both run on a small server, both connect to Telegram, WhatsApp, Slack and Discord, and both have published CVEs. Neither is a toy.

This is a docs-based comparison, not a benchmark. I have not run the same task on both agents, so nothing here is a head-to-head performance claim. Each claim carries its source: [docs] means the project's own README or documentation, [NVD] means the National Vulnerability Database API, and [observed] means I ran it myself. The one thing I did run is OpenClaw's install, for my OpenClaw self-hosting guide, which I tested on release 2026.10.5. If you are weighing a hosted consumer agent instead, see Meta Muse vs OpenAI Dots vs Grok Bot.

What each one is, from first principles

OpenClaw: an agent that lives in the channels you already use

OpenClaw began as Warelay in November 2025, became Clawdbot, was renamed Moltbot on 27 January 2026 after trademark complaints from Anthropic, and became OpenClaw three days later (Wikipedia's timeline). The README says it is stewarded by the OpenClaw Foundation, which employs the core team and signs releases, and lists donors including Amazon, Lobster Computer Company, Offline Holdings, OpenAI, Red Hat and the University of Michigan. It also states there is no paid tier, hosted service or token.

The README describes it as an assistant that runs on your own computer and meets you in Discord, iMessage, Slack, Teams, Telegram, WhatsApp and 20+ more channels, plus native apps for macOS, iOS, Android, Windows and Linux. One Gateway runs either a personal assistant on a laptop or a shared team deployment, and the README says configuration is the only difference. State, memory and credentials live on your hardware, and models and agent harnesses (Claude, Codex, local models) are plugins you can swap.

Sources: github.com/openclaw/openclaw README.

Hermes Agent: an agent built around a learning loop

Hermes Agent is Nous Research's entry in the same lane. Its README leads with a closed learning loop: the agent creates skills from experience, improves them during use, nudges itself to persist knowledge and searches its own past sessions, with FTS5 session search and LLM summarization for cross-session recall. One gateway process serves Telegram, Discord, Slack, WhatsApp, Signal and the CLI, and the messaging docs list many more platforms (below).

Sources: github.com/NousResearch/hermes-agent README.

Core architecture

The shape is similar: a gateway process, a swappable model layer, a channel layer and local files for memory. The emphasis differs. OpenClaw's docs foreground where you reach it from (channels, companion apps, nodes). Hermes's docs foreground where its commands run: six built-in terminal backends (local, Docker, SSH, Modal, Daytona, Vercel Sandbox) plus plugin backends such as Singularity/Apptainer, each with a different isolation guarantee [docs].

The comparison, point by point

Execution loop, API surface, browser and computer use

Both run a conventional observe-reason-act loop. OpenClaw has an agent-loop concept page in its docs. For API access, Hermes documents an API server that any OpenAI-compatible frontend can use, and OpenClaw's Gateway exposes a WebSocket API (the interface CVE-2026-25593 abused, below). OpenClaw can also act as an MCP server: openclaw mcp serve exposes channel conversations to another MCP client.

On device and browser control, OpenClaw's README says its companion apps and nodes add voice, Canvas, camera, screen and device-local actions, and its Docker sandbox backend can run a sandboxed browser. Hermes lists a Browser Use cloud browser through its Nous Portal Tool Gateway, and its README links a community computer-use-linux MCP server for Linux desktop control. Neither is a drop-in computer-use product; treat both as a tool you add and test.

Model and provider support

OpenClaw treats the model as a plugin: Claude, Codex or local models, swappable without touching the rest of the config. Hermes works with any provider and also offers Nous Portal, an optional subscription that the README says covers 300+ models plus a Tool Gateway for web search, image generation, text-to-speech and a cloud browser, switchable at runtime with /model. One bill is the Portal's selling point. Using a model you already pay for, with no aggregator in the loop, works on both.

Tool use and MCP

Both document MCP, and the first version of this article was wrong to say OpenClaw's MCP docs were thin. OpenClaw has a dedicated "Connect MCP servers" page: you add servers from the Control UI (Settings, then MCP) or config, choose Streamable HTTP, SSE or stdio transport, and verify with openclaw mcp doctor <name> --probe. Tools from a connected server go through the same tool-profile and tool-policy controls as everything else. Hermes has an MCP integration guide, and its security model includes MCP credential filtering, which strips environment variables from MCP subprocesses.

Memory and persistent context

The first version called this the sharpest architectural difference and described Hermes memory as opaque. The docs do not support that. Both keep memory as Markdown files you can read:

  • OpenClaw writes plain Markdown in the agent workspace (default ~/.openclaw/workspace): MEMORY.md for long-term facts, optional USER.md for preferences, and dated daily notes. The docs say the model only remembers what gets saved to disk. Files are indexed for memory_search (SQLite by default, with a PostgreSQL option).
  • Hermes keeps MEMORY.md (2,200 characters) and USER.md (1,375 characters) in ~/.hermes/memories/, injected into the system prompt as a frozen snapshot at session start. The agent edits them through a memory tool, memory does not auto-compact, and a write that exceeds the limit returns an error so the agent has to consolidate. Past sessions are searchable with FTS5.
  • Honcho, the dialectic user-modeling service, is an optional plugin on both sides: hermes plugins install honcho for Hermes, and an external Honcho plugin for OpenClaw.

So the real difference is size and ownership. Hermes memory is small, capped and agent-curated by design, and the learning loop pushes durable knowledge into skills. OpenClaw's workspace is files you and the agent both edit, with search over them. Hermes's docs also warn against pointing two agent processes at the same Hermes home, because automatic memory writes from two writers compound. I ran that case myself in my Hermes memory and skills lab: no lost writes, but duplicate facts.

Multi-agent support

Both document it, and the first version was wrong to call it undocumented for OpenClaw. OpenClaw has sub-agents (background runs spawned from an existing run, each in its own session, with results announced back and a configurable nesting depth) and separate multi-agent routing: several isolated agents in one Gateway, each with its own workspace, state directory and session store, mapped to channel accounts by bindings. Hermes has delegate_task, which spawns child agents with isolated context and their own terminal sessions, and only the child's final summary enters the parent's context.

Scheduling and automation

Both ship a scheduler. OpenClaw calls it Automations (openclaw automations, with openclaw cron as an alias): scheduled jobs, webhooks and Gmail PubSub triggers, with delivery to a chat channel, a webhook or nowhere. Hermes cron accepts natural language or cron expressions, can attach skills to a job, and has a no-agent mode that runs a script on a schedule and delivers its output with no model call.

Channels

The first version said OpenClaw's channel list was the longer one. That is out of date. OpenClaw's README says Discord, iMessage, Slack, Teams, Telegram, WhatsApp "and 20+ more", plus native apps. Hermes's messaging docs now list Telegram, Discord, Slack, WhatsApp, Signal, SMS, Email, Home Assistant, Mattermost, Matrix, Microsoft Teams, LINE and more. What is left is device integration and Home Assistant. OpenClaw's companion apps and nodes add voice, Canvas, camera and screen on its supported platforms [docs]. Hermes ships a Desktop app and an Android/Termux package, but I did not find an equivalent device-node feature in its README. Hermes lists Home Assistant, and OpenClaw's channel docs folder has no Home Assistant page. For the integration style question, see MCP servers vs. webhook automation.

Local vs. cloud execution

Both run the agent process locally. The model call is where they differ. OpenClaw's README says its prompts go to the provider and chat platforms you configure, so a local model keeps inference on the box. Hermes can point at a local or custom endpoint too, but its documented easy path is Nous Portal, a hosted subscription. If "nothing leaves this machine" is a hard requirement, either works, and with Hermes you make that choice on purpose instead of taking the default path.

Self-hosting and deployment model

OpenClaw needs Node.js 24.16+ or 26.1+ (Node 26 recommended). The README's installer provisions a supported Node when needed, and the npm route is npm install -g openclaw@latest --allow-scripts=openclaw on npm 12 or npm 11.16+ (older npm omits the flag). In my own install of 2026.10.5, Node 22 failed at install time, the gateway took 13 seconds to start, held about 1 GB idle, and restarted in 12 seconds after kill -9 [observed, from the self-hosting guide; one machine, loopback and token auth only].

Hermes's installer provisions pinned Python 3.14, Node.js, npm, ripgrep and FFmpeg for you, so the longer dependency list in the first version matters less than I said. I have not installed Hermes for this article, so I have no startup or memory figures for it. For the economics of self-hosting generally, see self-hosting on Docker and AI automation total cost of ownership.

Enterprise and on-prem deployment

I found no enterprise edition, SLA or support contract in either README or the docs I read. Both are community open-source projects, so a support contract means building your own runbook. OpenClaw's security guide is explicit that it assumes one trust boundary per gateway: a single operator, or a team whose members trust each other. See enterprise agentic AI in 2027 for how that shapes buying in this category.

Data privacy

The OpenClaw README says that by default it phones home for nothing but a daily version check, anonymous feature statistics are opt-in, and update.checkOnStart: false disables both. Hermes's privacy posture depends on the model and terminal backend you pick: a local model with a local or Docker backend keeps things on the box, while Nous Portal plus a cloud backend (Modal, Daytona, Vercel Sandbox) does not. Related: AI automation security and data privacy.

Security model and sandboxing

  • OpenClaw: sandboxing is off by default. The README says tools run on the host for the main session unless you configure sandboxing. The mode setting takes off (default), non-main or all, with docker (default backend), podman, ssh, openshell and crabbox backends. The docs call it "not a perfect security boundary". Unknown DM senders are paired by default, approved with openclaw pairing approve. Exec approvals gate commands for sandboxed agents that run on a real host, and the docs say approvals reduce accidental execution risk but are not a per-user auth boundary.
  • Hermes: eight documented layers, with isolation as the production recommendation. The layers are user authorization, dangerous-command approval, file write safety, container isolation, MCP credential filtering, context-file scanning, cross-session isolation and input sanitization. The docs recommend the docker, modal, daytona or vercel_sandbox backend for production gateways, because the container is then the boundary and command approval is skipped. The config docs show the local backend, which runs on the host with no isolation, and the docs state the file-write denylist is "defense-in-depth, not a hard boundary".

Neither default is wrong for a single trusted operator on their own machine. The moment a second person or any untrusted input reaches the agent, you need isolation on both. The mistake is assuming either one is sandboxed because it is popular.

Human approval mechanisms

Both put a human-in-the-loop gate in front of risky shell commands, and both say plainly that it is an accident guardrail. Hermes adds an always-on hardline blocklist that trips before the approval layer sees the command, plus user-defined deny rules. OpenClaw layers exec approvals on top of tool policy and elevated gating, and its docs note some full-session paths can skip host approval evaluation, so read the approvals page before relying on it.

Observability and debugging

I did not review either project's observability docs in depth, so I will not claim either lacks tracing: OpenClaw's README mentions an opt-in diagnostics export, and I have not checked what Hermes offers. What holds for any self-hosted gateway is that a service manager reporting "active" is not proof the agent is working. Build alerting around the agent's own logs and run real test messages. For the same point applied to evaluation, see AI agent evals for builders.

Developer experience and extensibility

Both are developer-first: CLI setup, config files and a skill or plugin system rather than a no-code builder. OpenClaw's skills are Markdown SKILL.md files with YAML frontmatter, loaded as bundled skills plus local overrides. Hermes skills follow the open agentskills.io standard, are created and refined by the agent itself, and install from a Skills Hub. I counted the Hermes repo's file tree on 2026-10-23: 58 bundled SKILL.md files under skills/ and 152 under optional-skills/. The first version said "about 160 bundled skills", which does not match either number.

Reliability for long-running tasks

Neither README makes a quantified uptime claim. The one reliability number I have is the OpenClaw restart time above (12 seconds after kill -9, on one machine), and I have no equivalent for Hermes. Long tool-using turns die at the smallest timeout in your stack, so raise the watchdog and every timeout above it together.

Cost structure

Both are MIT-licensed and free to run. Your cost is compute plus model spend: your own API keys on either, a local model for near-zero marginal cost, or Nous Portal if you want the optional Hermes subscription. I did not find a project-stated minimum server price for either, so size the server from your model and sandbox choice, not from a headline figure.

Major limitations

OpenClaw's biggest limitation is stated in its own docs: no sandbox by default and approvals that are not a security boundary, so you configure isolation if more than one trusted person touches it. Its NVD record is also far larger and more severe than Hermes's (next section), which is a reason to keep it patched and off the open internet. Hermes's biggest limitation is surface area: more terminal backends, a skill system the agent edits itself, and a hosted aggregator path to configure correctly. Its published CVEs include records against the context scanner and the memory scanner, the code meant to filter untrusted content.

Read these numbers with four caveats. The two queries use different matching (CPE for OpenClaw, keyword for Hermes), so the counts are not a controlled comparison. A CVE count measures how many issues were disclosed and recorded, not how many were exploited, and both projects draw heavy security research. Severity bands use the highest CVSS v3 score on each record. And scoring authority varies: the Hermes records I read were scored by VulDB as the CNA, with NVD analysis still "Deferred", while the OpenClaw ones I read were analyzed. With those limits, the gap in critical-severity records (54 against 0) is large enough to matter when you decide what to expose to the internet.

OpenClaw, examples checked against the NVD record:

  • CVE-2026-25253, CVSS 8.8, fixed in 2026.1.29. NVD says OpenClaw took a gatewayUrl from a query string and automatically opened a WebSocket connection, sending a token. runZero and the Belgian federal CERT describe it as a one-click remote code execution chain via that token exfiltration.
  • CVE-2026-25593, CVSS 8.4, fixed in 2026.1.20. An unauthenticated local client could use the Gateway WebSocket config.apply to set an unsafe cliPath later used for command discovery, enabling command injection as the gateway user.
  • CVE-2026-32922, CVSS 9.9 (v3.1; 9.4 on v4.0), fixed in 2026.3.11. A caller with operator.pairing scope could mint tokens with broader scopes through device.token.rotate and obtain operator.admin, which NVD says can lead to code execution on connected nodes.

Hermes Agent, examples checked against the NVD record:

  • CVE-2026-9366, CVSS 7.3 (v3.1), injection in _scan_context_content in agent/prompt_builder.py. The GitHub advisory lists 0.15.0 as the first patched version.
  • CVE-2026-7112, CVSS 5.6 (v3.1), improper authentication in the API server key check on v0.8.0. NVD's text rates the attack complexity as high.
  • Other records name components such as the command-approval guard (CVE-2026-9350, 7.3), execute_code (CVE-2026-9368, 7.3), the memory scanner (CVE-2026-10223, 6.3) and a webhook handler (CVE-2026-10224, 5.3). Several affect old versions, so check the affected range before assuming a current install is exposed.

The practical conclusion is the same for both and the numbers say it is more urgent for one: run a current release (OpenClaw v2026.10.6 and Hermes v0.22.5 as of 2026-10-23), sandbox tool execution, and do not expose the gateway to the open internet without reading the exposure guidance.

Real-world scenarios: which one, and why

Personal AI assistant. Either works. OpenClaw has the edge if you want the same agent on your phone and desktop with device nodes (camera, screen, device-local actions), which its README documents and I did not find for Hermes.

Server-hosted agent. Hermes's six terminal backends and container-first production guidance make a remote, isolated deployment the documented path. OpenClaw runs on a server as well, but sandboxing and exposure hardening are settings you turn on, and its security guide asks for separate gateways and credentials when users do not trust each other.

Telegram or WhatsApp chat agents. Both are listed for both. Choose by reading the specific connector's setup page, since connector quality varies per channel.

Scheduled jobs. Both have schedulers. Hermes accepts plain-language schedules and a no-model script mode. OpenClaw Automations add webhooks and Gmail PubSub triggers.

Coding. Both depend on the model you point them at. The framework-level difference is where commands run: a container backend on Hermes, or an enabled sandbox on OpenClaw, keeps an agent iterating on code away from your real host.

Research and knowledge work. Hermes bundles and optionally ships a larger skill library in its repo (58 and 152 skill files by my count). OpenClaw reaches the same tasks through its own skills and plugins.

Enterprise or on-prem. Neither has an enterprise edition. Both can run on-prem if your team accepts the operations load. See AI integration with legacy systems and AI automation governance for SMBs.

Privacy-sensitive teams. OpenClaw's README gives the more direct statement: state on your hardware, a daily version check as the only default phone-home, and local models as plugins. Hermes can match it with a local model and a local or Docker backend, but you configure away from Nous Portal's easy path.

Architectural trade-offs, in one place

This is a self-hosted against self-hosted comparison, so the usual hosted-agent trade-offs (losing control of your data, depending on someone else's uptime) do not apply to either side. What differs is where each project puts the controls. Memory is Markdown on both, so the contrast is a workspace you and the agent both edit (OpenClaw) against a small capped store plus a skill library the agent maintains (Hermes). Tool execution differs most: OpenClaw runs on the host unless you enable a sandbox mode, while Hermes documents isolation as the production default to choose. Orchestration is documented on both. Failure recovery on both is ordinary process supervision (systemd or Docker restart policies), which is your job either way. Lock-in is low: both are MIT, both use Markdown skills and memory, and the model layer is swappable.

Frequently Asked Questions

Is OpenClaw the same project as Clawdbot or Moltbot?

Yes. It began as Warelay, became Clawdbot, was renamed Moltbot on 27 January 2026 after Anthropic trademark complaints, and became OpenClaw three days later. It is now stewarded by the OpenClaw Foundation, an independent 501(c)(3).

Is Hermes Agent the same as Nous's Hermes models?

No. This article covers Hermes Agent, Nous Research's open-source agent (github.com/NousResearch/hermes-agent), not the separate Hermes family of fine-tuned language models. The agent can use many models, including through the optional Nous Portal subscription.

Are OpenClaw and Hermes Agent free?

Both are MIT-licensed and free to self-host. OpenClaw's README says it has no paid tier, hosted service or token. Your running cost is the server plus whatever model you connect, and a local model brings the marginal cost near zero. Nous Portal is an optional paid subscription for Hermes.

Is OpenClaw or Hermes Agent sandboxed by default?

Neither isolates command execution unless you configure it. OpenClaw's sandbox mode defaults to off, so tools run on the host for the main session. Hermes documents container backends (Docker, Modal, Daytona, Vercel Sandbox) as the production recommendation, while its local backend runs on the host.

Have OpenClaw or Hermes Agent had security vulnerabilities?

Yes, both. On 2026-10-23 NVD listed 575 records for OpenClaw (54 critical, highest CVSS 9.9) and 39 for Hermes Agent (none critical, highest 7.3), found with different matching methods. Counts reflect disclosure, not exploitation. Run a current release and sandbox tool execution.

Can I move from OpenClaw to Hermes Agent?

Hermes documents an importer: hermes import-agent openclaw, with --dry-run to preview. It brings over the persona file, memories, user-created skills, command allowlist and messaging settings, and API keys only if you pass --migrate-secrets.
