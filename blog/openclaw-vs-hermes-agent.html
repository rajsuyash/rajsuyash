OpenClaw vs Hermes Agent: The Full Comparison (2026)

Two MIT-licensed, self-hostable AI agents, two real CVE histories, and very different defaults for sandboxing and memory. A first-hand comparison for anyone about to put one on their own VPS.

If you’ve decided you want an AI agent that lives on hardware you control - not a hosted product you rent - the field narrows fast. Two projects dominate that specific lane right now: OpenClaw, the MIT-licensed, foundation-governed successor to Clawdbot/Moltbot, and Hermes Agent, Nous Research’s self-improving open-source agent. Both are free, both are self-hostable on a cheap VPS, both connect to Telegram/WhatsApp/Slack/Discord, and both have had real, numbered CVEs in 2026. Neither is a toy.

This is not a “which is more popular” piece. It’s the comparison I wished existed before I put both of them on my own VPS - what each one actually does with your shell, your model API keys, and your messages, and where each one will bite you if you don’t read the security docs first. If you’re instead evaluating a hosted, consumer-facing agent product rather than something you self-host, see our separate comparison, Meta Muse vs OpenAI Dots vs Grok Bot - this article is specifically about the self-hosted, open-source lane.

What each one is, from first principles

OpenClaw: an agent that lives in the channels you already use

OpenClaw’s history is unusual enough to be relevant: it started life as Clawdbot, built by indie developer Peter Steinberger, got a trademark objection from Anthropic in January 2026 over the name’s closeness to “Claude,” briefly became Moltbot, and then relaunched as the fully open-source OpenClaw - now stewarded by the independent OpenClaw Foundation, a 501(c)(3) nonprofit. OpenAI is listed as a donor to the Foundation, not an owner or operator. There is no paid tier, no hosted service, and no token.

The problem OpenClaw solves: most people’s “AI agent” experience is a chat tab they open and close. OpenClaw is instead a persistent local process - a Gateway running on your own machine or VPS - that you reach through the messaging apps you already have open: Discord, iMessage, Slack, Teams, Telegram, WhatsApp, Google Chat, Signal, and 20-plus others, plus native apps for macOS, iOS, Android, Windows, and Linux. State, memory, and credentials stay on your hardware as plain Markdown files. The model backend (Claude, Codex, or a local model via Ollama/LM Studio) is a swappable plugin, not something baked into the core.

Source: github.com/openclaw/openclaw, awesome-openclaw

Hermes Agent: an agent that’s supposed to get better the longer you run it

Hermes Agent is Nous Research’s entry in the same self-hosted lane, but with a different center of gravity: instead of positioning itself primarily as “an agent in your chat apps,” it leads with a closed learning loop. The agent is meant to create its own skills from the tasks you give it, improve those skills with repeated use, periodically nudge itself to persist what it’s learned, search its own past sessions, and build a standing model of who you are across sessions - rather than starting from a blank context every time.

The problem it solves: a stateless chat agent forgets everything between sessions and has to be re-taught the same context repeatedly. Hermes runs as a long-lived process - on a $5 VPS up to a GPU cluster or serverless backend - with memory, skills, and scheduled jobs that persist independent of any one conversation.

Source: github.com/NousResearch/hermes-agent

Core architecture

The shape is similar - a gateway process, a swappable model layer, a channel layer, local-first memory - but the emphasis differs in a way that matters operationally: OpenClaw’s docs foreground where you reach it from (channels, native apps); Hermes’s docs foreground where its commands actually execute (seven named terminal backends, each with a different isolation guarantee).

The comparison, point by point

Reasoning and execution loop, browser/computer use, and API surface

Both run a conventional observe-reason-act loop: receive a message or trigger, reason with the configured model, call tools, repeat until done, reply. Neither publishes a formal state-machine diagram of that loop, a first-class “computer-use” API, or a standalone versioned REST API reference distinct from the agent/gateway itself - treat all three as not publicly documented for either project beyond what’s implied by their general tool-calling and skill systems. If any of the three is a hard requirement, verify directly against current docs rather than relying on this comparison.

Model and provider support

OpenClaw treats the model as a plugin: Claude, Codex, or local models via Ollama/LM Studio (DeepSeek, Llama, Mistral, and others), swappable without touching the rest of the config. Hermes offers its own hosted aggregator - Nous Portal, a subscription giving access to “300+ models” - alongside direct OpenRouter, OpenAI, Anthropic, and custom-endpoint support, switchable at runtime with /model. If you want one bill covering many models without juggling individual API keys, Hermes’s Portal is the more turnkey option; if you want to point an agent at a model you’re already paying for elsewhere with zero aggregator in the loop, OpenClaw’s plugin model is more direct.

Tool use and MCP

Both support the Model Context Protocol. Hermes documents this plainly as “full MCP integration” for connecting external MCP servers. OpenClaw’s codebase references an MCP Registry integration, but a dedicated “attach an MCP server” walkthrough wasn’t located in this research pass - if MCP is your primary reason for choosing one of these, verify the current OpenClaw MCP docs directly before committing, since this is one area where the two projects’ documentation depth clearly differs.

Memory and persistent context

This is the sharpest architectural difference. OpenClaw’s memory model is deliberately simple and inspectable: plain Markdown files on your disk, nothing more exotic. You can read, edit, or grep your agent’s memory with a text editor. Hermes’s memory model is more ambitious and more opaque: agent-curated storage (the agent itself decides what’s worth keeping), FTS5 full-text search over past sessions, LLM-based summarization for cross-session recall, and - per Nous’s own docs - a “Honcho dialectic user modeling” component for building a standing model of the user. The trade-off is the classic one: OpenClaw’s memory is less magical and easier to audit; Hermes’s memory is more capable out of the box but harder to fully inspect, and depends on an LLM to decide what to remember.

Multi-agent support

Hermes documents isolated subagents for parallel workstreams as a named capability - spin off a sub-task into its own context rather than serializing everything through one loop. OpenClaw’s fetched docs don’t make an equivalent named claim; treat multi-agent orchestration as a Hermes-documented feature and not publicly documented for OpenClaw as of this research pass.

Workflow automation and cron

Both ship a built-in scheduler. OpenClaw’s docs list “cron jobs, hooks, and webhooks” as first-class capabilities. Hermes’s cron scheduler is explicitly described as natural-language-configurable (“daily reports, nightly backups, weekly audits… running unattended”) with delivery to any connected platform.

Integrations and channels

OpenClaw’s channel list is the longer, more exhaustive one in the fetched docs: 20+ messaging platforms plus five native app targets. Hermes’s named channel list (CLI, Telegram, Discord, Slack, WhatsApp, Signal, Email, Home Assistant) is shorter but notably includes Home Assistant, which OpenClaw’s fetched docs don’t call out - relevant if home/IoT automation is in scope. For a broader look at how MCP-based tool integration compares to classic webhook automation, see our piece on MCP servers vs. webhook automation.

Local vs. cloud execution

Both default to local-first execution of the agent process itself. Where they diverge is the model call: OpenClaw can go fully offline with a local model via Ollama/LM Studio; Hermes’s most turnkey path (Nous Portal) is a hosted model aggregator, though it supports pointing at local/custom endpoints too. If “no outbound call ever leaves this box” is a hard requirement, OpenClaw’s local-model path is the more direct route to that outcome today.

Self-hosting and deployment model

Both are built to self-host, and both run on genuinely small hardware. OpenClaw needs Node.js 24.16+ (or 26.1+) and installs via a bash/PowerShell script or npm install -g openclaw@latest; a Docker image is published, with a community-maintained image (coollabsio/openclaw) also available. Hermes needs Python 3.14, Node.js, npm, ripgrep, and FFmpeg, installs via a curl/PowerShell one-liner, and Nous’s own docs describe it as running on “a $5 VPS, GPU clusters, or serverless infrastructure” - with an official hardened Docker image, plus Singularity, Modal, Daytona, and Vercel Sandbox as first-class deployment targets. For more on the general economics of running your own automation stack instead of a SaaS, see self-hosting on Docker and AI automation total cost of ownership.

Enterprise and on-prem deployment

Neither project publishes an enterprise edition, SLA, or dedicated on-prem support contract in the sources retrieved for this piece - both are, as of this research, community open-source projects rather than vendor-backed enterprise products. That’s not publicly documented as a gap to fill with a sales call; if you need a support contract, you’re building your own ops runbook around either one. See our broader take on enterprise agentic AI in 2027 for how that reality is shaping enterprise buying in this category generally.

Data privacy

OpenClaw’s stated default is the stronger privacy posture on paper: state, memory, and credentials stay on your hardware, and the project phones home for nothing but an optional daily version check (which you can disable). Hermes’s privacy posture depends heavily on which model/terminal backend you choose - a fully local model plus a local or Docker terminal backend gets you close to the same posture; Nous Portal plus a cloud terminal backend (Modal/Daytona/Vercel Sandbox) does not. Related reading: AI automation security and data privacy.

Security model and sandboxing

Here the two projects make genuinely opposite default choices, and this is worth reading twice before you deploy either one:

  • OpenClaw sandboxes nothing by default. Tools run directly on the host for the main session unless you explicitly configure sandboxing. Unknown DM senders are paired (approved) via openclaw pairing approve, and an exec-approvals allowlist (~/.openclaw/exec-approvals.json) can gate command execution - but OpenClaw’s own docs are explicit that this is “an operator guardrail to reduce accidental command execution, not a multi-tenant authorization boundary.”
  • Hermes pushes you toward isolation by default for production. Its docs name Docker, Modal, Daytona, and Vercel Sandbox as the recommended terminal backends for a production gateway specifically because isolating commands from the host removes the need for manual dangerous-command approval. The official Docker image runs as an unprivileged user (uid 10000) via gosu, not root.

Neither default is automatically “wrong” - OpenClaw’s host-execution default is faster to set up for a single trusted operator on their own machine; Hermes’s isolation-first guidance is the safer default the moment more than one person, or any untrusted input, touches the agent. The mistake is assuming either one is sandboxed just because it’s a mature, widely-used open-source project.

Human approval mechanisms

Same mechanism on both sides - a human-in-the-loop gate before a risky shell command runs - with the same honest caveat from OpenClaw’s own docs that applies equally to Hermes’s: it’s an accident guardrail, not a security boundary against a determined, authenticated bad actor who already has access.

Observability and debugging

Neither project’s fetched docs describe a dedicated tracing/observability product (nothing equivalent to a hosted eval or trace dashboard). Both rely on local logs - in practice, journalctl/systemd logs for whichever one you’ve wired into a service manager. First-hand note: on a VPS running one of these behind systemd, a service reporting “active/running” is not proof the agent is actually working - a stale state-migration file once blocked an entire chat channel from starting while systemd reported the unit healthy the whole time; the real signal was only in the service’s own journal output. If reliable alerting matters to you, build it around the agent’s own logs, not the service manager’s status flag. For a parallel discussion of why “it’s technically running” isn’t the same as “it works,” see AI agent evals for builders.

Developer experience and extensibility

Both are developer-first: CLI-driven setup, config files, and a plugin/skill SDK rather than a no-code builder. Hermes’s skill system is the more structured of the two on paper - compatible with the open agentskills.io standard, ~160 bundled skills, a community Skills Hub, and autonomous extensibility (the agent creates and refines its own skills during use, not just loads skills you write). OpenClaw’s Tools/Skills/Plugins split plus ClawHub sharing covers similar ground more conventionally: you write a tool/skill/plugin against its SDK and it runs, without the self-authoring layer.

Ease of setup

Both install with a single script and run on a cheap VPS. Hermes has a slightly longer dependency list on paper (Python 3.14 specifically, Node.js, npm, ripgrep, FFmpeg) versus OpenClaw’s single Node.js runtime requirement - in practice this is a rounding error for anyone comfortable with a VPS, but it’s a real difference if you’re trying to keep a minimal attack surface and dependency count.

Reliability for long-running tasks

Neither project’s fetched docs make a quantified reliability claim (uptime %, MTBF, etc.) - not publicly documented for either. The practical failure mode worth knowing about is generic to any self-hosted agent gateway, not specific to either product: a long tool-using turn dies at whichever timeout in your stack is smallest, and an unconfigured watchdog can silently sit below every other timeout you deliberately raised. See the first-hand note under Observability above.

Cost structure

Both are MIT-licensed and free to run; your real cost is compute plus model API spend. OpenClaw’s floor is near-zero if you run a local model. Hermes’s floor is the VPS cost (“$5 VPS” per Nous’s own framing) plus whatever model billing you choose - Nous Portal subscription, or your own OpenAI/Anthropic/OpenRouter keys.

Major limitations

OpenClaw’s biggest limitation is the one its own docs state plainly: no sandboxing by default, and an exec-approvals system that is explicitly not a security boundary - you have to actively configure isolation if more than one trusted person touches it. Hermes’s biggest limitation is the inverse kind of complexity: more moving parts (seven terminal backends, a more elaborate memory system, a hosted model aggregator) means more surface area to configure correctly, and its own published CVE history (below) includes an injection vulnerability in the memory-scanning code itself - the part of the system specifically meant to keep untrusted content from reaching the model unfiltered.

Who should avoid each

If you want “install and forget” with no security configuration decisions, avoid both - both require you to actively read and apply the sandboxing/approval docs, not just install and connect a messaging channel. If you specifically need a vendor support contract or a formal enterprise SLA, avoid both as currently published (self-support is the model for both).

Published security track record: neither is “the safe one”

It’s tempting to assume one of these two projects is simply “the secure one.” The documented record doesn’t support that story - both have real, publicly disclosed CVEs in 2026, spanning the categories that matter most for an agent with shell and messaging access.

OpenClaw, independently confirmed: - CVE-2026-25253 (“ClawBleed,” CVSS 8.8) - one-click RCE via auth-token exfiltration over WebSocket, affecting versions before 2026.1.29. Also covered by the Belgian federal CERT (ccb.belgium.be) and NVD. - CVE-2026-25593 - unauthenticated local RCE via the Gateway WebSocket’s config.apply, which could set an unsafe cliPath later abused for command injection. Also in NVD. - CVE-2026-32922 - a CVSS 9.9 privilege-escalation vulnerability in device-pairing token rotation (device.token.rotate), affecting OpenClaw before 2026.3.11. This one is in NVD: a paired, lower-privilege device can escalate to full control by abusing the rotate endpoint. Patch to 2026.3.11 or later.

Hermes Agent, independently confirmed: - CVE-2026-9366 - an injection vulnerability in agent/prompt_builder.py’s context-scanning code, fixed in 0.15.0. Also in NVD. - CVE-2026-7112 - an authentication bypass in the API server’s key-check handler, affecting v0.8.0. Also in NVD. - Additional reported CVEs cover injection in the memory tool, uncontrolled resource consumption in a webhook handler, and a sandbox-related issue in code execution - all named against NousResearch/hermes-agent specifically, ruling out confusion with an unrelated package of the same name.

Both projects give an agent broad access to your shell, messages, and model API keys by design, and both attract real security research. A clean CVE history on either side would be the surprise. The practical conclusion isn’t “avoid both” - it’s “patch promptly, sandbox by default, and don’t expose the gateway to the open internet without reading the exposure-runbook docs.”

Real-world scenarios: which one, and why

Personal AI assistant. Either works; OpenClaw’s broader native-app and channel list (20+ platforms, five native OS targets) gives it a slight edge if you want the same agent reachable from everything you already use.

VPS-hosted agents (the author runs both this way). Hermes’s explicit “$5 VPS, GPU cluster, or serverless” framing and first-class Modal/Daytona/Vercel Sandbox backends make it marginally more “designed for” a remote server from day one. OpenClaw runs equally well on a VPS, but its docs frame the default use case more around a personal machine you’re sitting in front of - sandboxing and remote-exposure hardening are something you add, not something that ships configured.

Telegram/WhatsApp chat agents. Both are strong here; Hermes additionally names Signal and Home Assistant, which matters if your chat surface extends into home automation. Pick based on which messaging platform’s connector you trust more after reading its specific setup docs - not a general preference, since connector quality varies per channel in both projects.

Cron/scheduled jobs. Both ship built-in schedulers. Hermes’s natural-language cron framing is more approachable for non-technical schedule authoring; OpenClaw’s “cron jobs, hooks, and webhooks” framing is more conventional/ops-native if you’re already comfortable with cron syntax.

Coding. Both are entirely dependent on which model you point them at (Claude, Codex, GPT, or a local model) - neither project’s own coding ability is meaningfully differentiated from the other at the agent-framework layer. The differentiator is tool/terminal safety while coding: Hermes’s isolated terminal backends are the safer default for letting an agent run and iterate on code without touching your real host.

Research. Hermes’s bundled ~160 skills include dedicated research skills (arXiv, web search) out of the box; OpenClaw achieves the same through its own Tools/Skills/Plugins ecosystem, but with less of a pre-built library documented in the sources retrieved here.

Enterprise/on-prem. Neither has a formal enterprise edition as of this research. Both are workable on-prem if your team is comfortable owning the ops burden yourself - see our take on AI integration with legacy systems and AI automation governance for SMBs for the broader considerations that apply regardless of which agent framework you pick.

Privacy-sensitive industries. OpenClaw’s local-first, Markdown-on-disk memory and local-model path give it the more direct route to “nothing leaves this box.” Hermes can match that with a local model and a local/Docker terminal backend, but its most turnkey path (Nous Portal) is a hosted aggregator by default - if privacy is the binding constraint, you’ll spend more time configuring Hermes away from its easiest path than configuring OpenClaw toward its easiest path.

Architectural trade-offs, in one place

Pulling the thread through everything above: this is a self-hosted-vs-self-hosted comparison, not hosted-vs-self-hosted (that’s Meta Muse vs OpenAI Dots vs Grok Bot), so the usual hosted-agent trade-offs - losing control of your data, being stuck on someone else’s uptime - don’t apply to either side here. What does differ is where each project puts the controls. Context and memory management is OpenClaw’s simple, auditable Markdown files versus Hermes’s more capable but more opaque agent-curated/LLM-summarized store. Tool execution and permissions, and sandboxing, are the sharpest divide: host-execution-by-default-with-an-accident-guardrail (OpenClaw) versus isolation-recommended-for-production (Hermes) - pick based on your actual trust model, not on which framing sounds safer. Orchestration is asymmetric: Hermes documents isolated subagents, OpenClaw doesn’t make an equivalent claim in the sources reviewed. Failure recovery on both sides is standard process supervision (systemd/Docker restart policies) rather than anything agent-specific - that part is on you either way, and reliability is bounded by the timeout-layering trap described above for both. Vendor lock-in is genuinely low for both - MIT license, no proprietary data format, swappable model layer - with the only real stickiness being time invested in one project’s specific skill format (ClawHub-style vs. agentskills.io-compatible), which is inconvenient to port, not a hard lock-in.

Which one should you choose?

Choose OpenClaw if you want the simplest possible memory model to audit (plain Markdown files), the broadest channel/native-app reach, a fully offline local-model path, and you’re comfortable actively configuring sandboxing yourself rather than getting it by default.

Choose Hermes Agent if you want a more structured, self-improving skill system out of the box, isolated terminal backends that make “safe by default” the easier path for production, built-in natural-language cron, and you’re fine with Python being part of your dependency stack.

Neither is right if you need a vendor support contract, a formal enterprise SLA, or an agent you can deploy without reading any security documentation at all - both require you to actively engage with sandboxing/approval configuration, and neither publishes an enterprise edition as of this research.

Frequently Asked Questions

Is OpenClaw the same project as Clawdbot or Moltbot?

Yes - one continuous project, renamed after a January 2026 Anthropic trademark objection to “Clawdbot,” now governed by the nonprofit OpenClaw Foundation.

Is Hermes Agent the same as Claude's "Hermes" models?

No. This article covers Hermes Agent, Nous Research’s open-source agent framework (github.com/NousResearch/hermes-agent) - not Nous’s separate “Hermes” family of fine-tuned LLMs, which is a model, not an agent.

Are OpenClaw and Hermes Agent free?

Both are MIT-licensed and free to self-host. Your ongoing cost is compute (from roughly $5/month for Hermes, per Nous’s own framing) plus whatever model API you connect - a local model can bring that near $0.

Is OpenClaw or Hermes Agent sandboxed by default?

No, not fully, in different ways. OpenClaw runs tools on the host by default unless you configure sandboxing. Hermes’s production guidance recommends isolated terminal backends (Docker, Modal, Daytona, Vercel Sandbox) - but you still have to choose one; it isn’t universal across every install path.

Have OpenClaw or Hermes Agent had security vulnerabilities?

Yes, both - publicly disclosed 2026 CVEs including RCE and auth-bypass issues on each side (see the security section above). Both patch actively; run a current version and read the security docs before exposing a gateway or connecting a channel.

Can I run either one fully offline, with no cloud model calls?

OpenClaw, yes directly, via Ollama/LM Studio. Hermes can also point at a local endpoint, but its most turnkey path (Nous Portal) is a hosted aggregator by default, so offline takes a deliberate config choice rather than being the easy path.

Does either one support the Model Context Protocol (MCP)?

Yes, both. Hermes documents “full MCP integration”; OpenClaw’s codebase references an MCP Registry. If MCP depth is decision-critical, verify OpenClaw’s current MCP docs directly - documentation depth here differs between the two.

Which one is better for a VPS-hosted personal assistant?

Either, depending on priorities: OpenClaw for the simplest-to-audit memory and broadest messaging reach; Hermes Agent for a self-improving skill system, natural-language scheduling, and isolation-by-default production guidance. Both are genuinely production-usable self-hosted today.
