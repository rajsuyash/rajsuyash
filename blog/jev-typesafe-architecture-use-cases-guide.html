JEV (TypeSafe Jev) Guide: Architecture, Use Cases, Limits

Jev isn't an agent framework, and treating it like one is the fastest way to misuse it. What TypeSafe's System One model actually does, where it fits next to LangGraph and CrewAI, and when it earns a place in your stack.

If you’ve searched “JEV AI agent” recently, you’ve probably landed on three different things without realizing it. This guide is about Jev, the first “System One model” from TypeSafe AI — the one with real docs, a real API, and a real funding history. It is not about jev-ai.org, an independent community app for sharing “Jev playbooks” whose own README says plainly it “is not the official product site for the underlying Jev model.” And it’s not about AgentJev-0.6B, an unrelated, fully open-source, self-hostable 0.6B decision model that happens to benchmark itself against TypeSafe’s Jev. Three names, one letter of difference, three different things to build on. We’re covering the real one.

If you came here expecting a comparison against custom AI agent development platforms like Claude Code or OpenClaw: that’s not quite the right lens, and the first section explains why.

The one-paragraph verdict

Jev is not an agent framework. It doesn’t run a loop, hold memory, call tools, or orchestrate anything. It’s a decision primitive: you send it some text and a set of typed questions with a fixed answer space, and it sends back typed answers with calibrated probabilities — in one pass, in well under a second, for a fraction of a cent. Think of it less as “an alternative to LangGraph” and more as “a faster, cheaper, more honest if/switch statement for the cases where the condition is semantic, not literal.” Keep that frame and the rest of this guide will make sense; lose it and you’ll keep asking questions Jev’s docs never answer, like “does it have memory” (no) or “can I self-host it” (no).

1–3. What JEV is, why it exists, the problem it solves

TypeSafe AI’s own framing is refreshingly specific: “Large language models (LLMs) are designed to produce text for humans to read. When you need a model to make a judgment that your code will consume, that creates a mismatch.” Normal LLM-in-the-loop code pays for this mismatch constantly — you ask a chat model to classify a support ticket, it replies with a sentence, you regex or JSON-parse that sentence, and occasionally it hallucinates a category that was never in your list, wraps the answer in markdown, or refuses outright.

Jev’s answer is to remove the text-generation step entirely for this class of problem. You define the possible answers up front (a Choice’s options, a Noul’s yes/no, a Score’s rubric levels); the model picks among exactly those, with a probability. It’s the same instinct behind the RPA-vs-AI-automation distinction this site has made before, pushed one step further: rules are too brittle for semantic judgment, but a full generative model is often more power (and more failure surface) than a bounded decision needs. Jev sits in between.

TypeSafe AI itself is a young company — founded in 2024, came out of stealth on September 15, 2026 with Jev in early access alongside a $40M seed round led by DCVC. That timeline matters for the maturity-risk section near the end.

4–5. How the architecture works, and the core components

A System One model call is one HTTP request with two inputs and one output shape:

Every question in a request is answered in one parallel pass — the model can’t use one answer to inform another within the same call, so a second request is only needed when an earlier answer determines what to even ask next. There are exactly three question types:

Primitive What it answers Returns Example
Choice “Which of these options?” the chosen option + a probability distribution over all options + confidence tone: calm / frustrated / angry
Noul “Is this true?” probability of “yes,” 0–1, no separate confidence field billing: is this about billing?
Score “Where on this rubric?” a probability-weighted position on 2–10 ordered levels + confidence urgency: can wait / this week / today

Because the model never emits free text, TypeSafe’s claim is that it structurally “cannot produce a type error or a hallucinated value” — the possible outputs are fixed before the call runs. That’s a real architectural property, not a guarantee the chosen answer is correct; a Choice can still confidently pick the wrong option. That gap is exactly what confidence scoring is for (§13).

6–7. Installation, deployment model, and supported models

There’s no install in the traditional sense — Jev is a hosted API, called directly or through an SDK:

pip install typesafe-sdk        # Python
npm install @typesafe-ai/sdk    # Node 20+

from typesafe_sdk import TypeSafeClient, Choice, Noul, Score

with TypeSafeClient() as client:  # reads TYPESAFE_API_KEY from env
    response = client.system_one(
        state={"document": "I was charged twice. Please fix this ASAP."},
        questions={
            "billing": Noul(instructions="Is this ticket about billing?"),
            "tone": Choice(instructions="What is the customer's tone?",
                            criteria={"calm": None, "frustrated": None, "angry": None}),
            "urgency": Score(instructions="How urgent is this ticket?",
                              criteria=["can wait", "this week", "today"]),
        },
    )

The current production model is jev-1.13.0. Two aliases, jev-latest and jev-preview, both currently point to it — but TypeSafe’s own docs warn that aliases “move when new releases ship, potentially changing results without code changes,” and recommend pinning the versioned ID once you’ve tuned confidence thresholds against a specific model’s behavior. That’s a detail most teams will only learn the hard way if they don’t read it here first.

8–11. Tool integrations, memory, MCP support, and the API

Tool integrations and MCP: TypeSafe does not ship an official MCP server. What exists is a real, if scattered, community ecosystem that calls Jev’s API and exposes it as tools inside other agents — jev-mcp (at least two independent implementations), typesafe-mcp/system-one-connector (a Go single-binary MCP server for Claude Desktop), decisions-judge-mcp, and jev-shield (a “semantic MCP firewall” that screens tool calls through a Jev judgment before they execute). If you want Jev inside Claude Code, Cursor, or Codex, this is the honest comparison point to MCP server vs. webhook automation: you’re choosing a third-party bridge, not a first-party integration.

Memory: there isn’t any. Every /v1/systemone call is stateless — you send the full state every time. No session, no conversation history, no persistent store. If your use case needs memory, that’s your application’s job, not Jev’s — a real difference from frameworks like Hermes or OpenClaw, which build persistent memory in by default (more on that below).

The API itself, verified directly against the docs: - POST https://api.typesafe.ai/v1/systemone, Authorization: Bearer <key> - Request: state, model (e.g. "jev-latest"), questions - Response: model, answers (keyed to your question IDs), usage (token counts) - Errors: 401 bad key, 422 malformed request, 429 rate limited, 529 overloaded; SDKs retry with backoff automatically - Rate limits (published, “subject to change”): 100,000 tokens/sec, 80 requests/sec

12–13. Security and permissions

TypeSafe publishes a privacy policy, a data-processing addendum, a master customer agreement, acceptable-use policy, and a Trust Center. The commitments stated there: no training on customer data, no selling/sharing of personal data under CCPA definitions, and zero data retention (ZDR) available for enterprise customers on request. What’s not there, as far as this research found: any SOC 2, ISO 27001, HIPAA, or comparable third-party certification. If your procurement checklist needs one, that’s currently a “not publicly documented” — worth confirming directly with sales before you commit, which is the same advice this site gives in how to evaluate an AI vendor’s data-privacy claims.

One correction worth flagging because it’s an easy mix-up: you’ll find pages claiming Jev’s “self-hosted build includes SSO, RBAC, and SCIM.” That claim describes a third-party MCP wrapper’s own deployment option, not a TypeSafe enterprise tier — TypeSafe’s own enterprise security story is ZDR plus the legal documents above, nothing more granular published.

Permissions work the same way memory does: there’s no RBAC on the API itself. TypeSafe’s actual permission model is confidence-based, and it’s the most genuinely useful idea in the whole product. Three tiers, straight from their docs: at high confidence, act automatically; at medium confidence, confirm with a user or flag for review; at low confidence, escalate to a human or fall back to another system. Crucially, the threshold isn’t fixed — TypeSafe’s own guidance is that it should scale with the cost of being wrong (a read-only lookup can act at low confidence; a destructive action should require 0.9+ or an explicit human confirmation). That’s a cleaner mental model for human-in-the-loop gating than most agent frameworks ship with, and it maps directly onto building an approval policy around AI decisions.

14–15. Self-hosting and scalability

Jev cannot be self-hosted. No downloadable weights, no on-prem build, nothing in the docs or terms suggesting otherwise — confirmed by the absence on TypeSafe’s own pages and independent third-party write-ups reaching the same conclusion. (Don’t confuse this with AgentJev-0.6B, the unrelated open-weight model mentioned up top — that one you genuinely can self-host, but it isn’t Jev.) If you’re already running self-hosted n8n on Docker for data-residency reasons, Jev’s hosted-only model is a real constraint to weigh, not a detail to skip past.

Scalability, for the hosted service, is whatever TypeSafe’s published limits allow: 100K tokens/sec and 80 requests/sec by default, explicitly described as “adjusting dynamically” under demand, with higher tiers presumably available by contacting sales — no specific enterprise-tier numbers are published.

16–17. Observability and enterprise readiness

Observability is thin: each response includes usage (input/output token counts), and that’s the extent of what’s documented — no tracing dashboard, no request-log UI, no built-in eval harness. If this matters to you, it’s worth reading what to measure before you ship an agent and building your own logging around every /v1/systemone call, because TypeSafe isn’t giving you one.

Enterprise readiness is best read through the company’s age, not its marketing copy: seed-stage (closed September 2026), product in early access, legal/privacy infrastructure in place, no public security certifications found, rate limits still described as actively changing. None of that is disqualifying — plenty of production systems run on seed-stage vendors — but it belongs in the same conversation as enterprise AI budget planning: budget for vendor risk, not just token cost.

18. Limitations, summarized

Text-only input (no image/audio/video yet); no memory; no self-hosting; no official MCP server; stateless by design; model aliases that can silently drift; rate limits still being tuned; no published compliance certifications; and — the one that matters most for scoping a project correctly — it is not an agent. It doesn’t plan, it doesn’t call tools, it doesn’t hold a conversation. It answers bounded questions about data you hand it, nothing more, nothing less.

Where JEV fits inside a real agent

This is the composition pattern behind every real-world Jev integration found in this research: it’s a node inside a larger system that someone else owns, never the system itself.

Best use cases

Each section below is labeled by its grounding: [official] means TypeSafe’s own use-case map covers it directly; [community] means it’s a documented third-party project built on Jev; [composed] means it’s a reasonable architecture you’d build using Jev as one piece, not something TypeSafe itself ships or documents as a named category; [author’s pilot] draws on the writer’s own small-scale usage.

Personal agents — [composed]

Problem: A personal assistant (email triage, calendar requests, task capture) drowns in borderline decisions — is this urgent, is this actually a task, which project does this belong to — long before it needs to write anything. Why JEV fits: These are all bounded, repeated, narrow-answer-set judgments — exactly Jev’s sweet spot — running at a volume where paying full LLM-reasoning cost on every item is wasteful. Suggested architecture: Inbound item → Jev (Choice over project/category, Noul for “is this actionable,” Score for urgency) → confidence-gated routing → only genuinely ambiguous or high-stakes items reach a reasoning LLM or the human. Example workflow: This is close to the author’s own compiler front-stage pilot below, generalized to a personal inbox rather than a dev-log compiler. Limitations: No memory of past decisions across calls — your app has to track “I already classified this one” and feed Jev the right state each time.

Enterprise assistants — [official-adjacent]

Problem: An internal assistant fielding thousands of employee requests (IT tickets, HR questions, expense queries) needs consistent, auditable triage before any generative step. Why JEV fits: TypeSafe’s own use-case map names recruiting (candidate-vs-criteria matching) and customer support (ticket classification, issue extraction, churn-risk detection) directly; internal enterprise assistants are the same shape pointed inward. Suggested architecture: Request → Jev classifies department/urgency/sensitivity → deterministic routing to the right queue or knowledge base → LLM drafts a response only after routing is settled → confidence-gated human review for anything below the department’s risk threshold. Example workflow: Employee message → Choice (IT/HR/Finance/Facilities) + Score (urgency) + Noul (contains sensitive PII) → route, and only escalate to a human reviewer when the PII Noul fires or urgency hits “today.” Limitations: No enterprise RBAC in the API itself — the department-routing logic and audit trail are entirely your code’s responsibility, and no compliance certification exists yet if that routing touches regulated data.

AI engineering agents — [community]

Problem: Coding agents burn tokens and time re-reasoning about things that are really just classification: is this diff safe to auto-apply, which model is cheap enough for this subtask, is this tool call still relevant to the current goal. Why JEV fits: This is the single best-documented community category. Real, named projects: jev-router picks the cheapest sufficient model for a Claude Code request; fast-jev-compaction replaces LLM-generated context summaries with Jev scoring of tool calls; foreman uses Jev decisions to keep a long-running coding agent on task; jev-review runs a staged code-review workflow. Suggested architecture: Coding agent’s tool-call loop → before each expensive LLM call, ask Jev a cheap Choice/Score (“does this subtask need the frontier model, or will the cheap one do?” / “is this tool call still relevant to the stated goal?”) → route accordingly. Example workflow: This mirrors the owner’s own skill-picker build: 444 candidate skills split into 6 groups of 80 (Jev’s Choice caps at 255 options), a Choice per group, then a final Choice among the group winners — not open-ended reasoning about which skill fits, a bounded pick. Limitations: These are all third-party, unmaintained-by-TypeSafe repos — evaluate them like any other dependency, not like an official SDK.

Research — [official]

Problem: Literature review and evidence work (screening papers, labeling transcripts, verifying citations) is mostly “does this match these criteria,” repeated thousands of times. Why JEV fits: Named directly in TypeSafe’s use-case map: “screen papers, label transcripts, verify citations, identify entities.” Suggested architecture: Candidate document/passage → Jev Noul/Choice against inclusion criteria → only passages that pass go to a reasoning model for synthesis or to a human for final judgment. Example workflow: 2,000-paper corpus → Noul (“does this paper report an RCT?”) at low cost per paper → the ~200 that pass go to a slower, more expensive synthesis step. Limitations: Jev can’t read PDFs or figures (text-only state today); someone still has to extract clean text first.

Customer support — [official]

Problem: Ticket triage, issue extraction, churn-risk flagging, and verifying that a drafted response actually answers the question — all bounded judgments that currently eat generative-model budget for no reason. Why JEV fits: Named directly in TypeSafe’s use-case map, with the same four examples given there: classify, extract, detect churn risk, verify responses. Suggested architecture: Ticket → Jev (Choice category, Score urgency, Noul churn-risk) in one parallel pass → route to the right queue → an LLM drafts a reply → a second Jev Noul (“does this reply actually address the stated issue?”) gates the send. Example workflow: Exactly the request/response shape shown in TypeSafe’s own SDK example (billing/tone/urgency on a single ticket). Limitations: Verifying a drafted reply with Jev checks a narrow, stated condition — it isn’t a substitute for a real quality-eval pipeline (see what to measure before you ship an agent).

Sales automation — [official]

Problem: Lead scoring and company-fit evaluation at outbound volume, where a generative model per lead is both slow and expensive. Why JEV fits: Named directly: “lead generation: score company fit and detect purchase intent.” Suggested architecture: Enriched lead data → Jev Score (fit) + Noul (buying-intent signal present) → only leads above threshold reach a human SDR or a generative outreach-drafting step. Example workflow: Firmographic + signal data as state → Score against an ICP rubric → top decile routed to outreach. Limitations: Scoring quality is bounded by what’s in state — garbage firmographic data in, garbage score out; Jev doesn’t enrich data itself.

Internal knowledge systems — [official-adjacent]

Problem: Knowledge graphs and internal wikis decay because nobody has time to check whether a new document contradicts an existing entry or which entity it actually refers to. Why JEV fits: TypeSafe names “knowledge graphs: annotate relationships, detect contradictions, verify entities” directly. Suggested architecture: New document → Jev Noul per existing related-entity candidate (“does this contradict entity X?”) → flagged contradictions go to a human curator; clean annotations merge automatically. Example workflow: Candidate entity pairs pulled by a retrieval step → Jev judges relationship type via Choice → graph updates only on high-confidence answers. Limitations: Candidate generation (finding which entities to check against) is still your retrieval system’s job — Jev only judges pairs/documents it’s shown.

Data analysis — [official-adjacent]

Problem: Turning free-text fields (survey responses, call notes, reviews) into structured features for downstream analysis or ML, without hand-labeling thousands of rows. Why JEV fits: “Feature extraction: convert natural-language data into probabilistic features for ML models” is a named category, as is big-data processing more broadly. Suggested architecture: Row of free text → one or more Jev Score/Choice questions per feature → write probability-weighted features back into the dataset → standard ML/BI tooling downstream. Example workflow: Customer-review text → Score (sentiment, 2–5 levels) + Choice (topic) as two new structured columns, computed at scale. Limitations: Rate limits (100K tok/sec, 80 req/sec by default) cap how fast you can batch this; large one-off backfills may need to be paced or you’ll hit 429.

Workflow automation — [composed]

Problem: No-code/low-code automations (the kind built in n8n) frequently need one semantic branch point — “which of these five paths does this input belong on” — surrounded by entirely deterministic steps. Why JEV fits: It’s a cheap, fast node you can drop into an otherwise-deterministic pipeline instead of reaching for a full LLM call at every branch. Suggested architecture: n8n (or similar) HTTP Request node → Jev /v1/systemone → branch node reads the returned Choice/Noul to pick the downstream path. Example workflow: This is directly comparable to the trade-off described in MCP server vs. webhook: when the server wins — if the workflow already knows which branch it wants, a plain webhook/HTTP step is simpler than paying for a judgment call at all; Jev earns its place only when the branch genuinely depends on unstructured input. Limitations: Not a native n8n node — it’s a generic HTTP Request call you wire up yourself; no visual-builder integration exists today.

DevOps — [composed, with one academic citation]

Problem: Alert fatigue and false-positive triage — deciding whether a finding, an anomaly, or a severity rating is real before paging a human or an expensive remediation agent. Why JEV fits: A 2026 arXiv paper on autonomous penetration-testing harnesses uses exactly this pattern: Jev as a non-generative “System One” decision layer for finding adjudication, severity recalibration, agent pruning, and confirmation loops, specifically to avoid using the same generative model for both finding issues and validating them. Suggested architecture: Monitoring/scanning tool output → Jev judges severity/validity/relevance → only validated, appropriately-scored findings page a human or trigger remediation. Example workflow: Security scanner’s raw finding → Score (true severity, re-calibrated) + Noul (likely false positive) → suppress low-severity/likely-false-positive noise before it reaches an on-call engineer. Limitations: This pattern is documented in an academic paper, not a TypeSafe product page — treat it as a credible architecture proposal to adapt, not an off-the-shelf DevOps integration.

Browser automation — [community]

Problem: Browser agents waste cycles asking a full multimodal/reasoning model “which element do I click” on every single step. Why JEV fits: Community projects already do this on accessibility trees rather than screenshots: jev-android (Kotlin SDK for UI automation via the Android accessibility tree) and jev-mobile (System One decisions per accessibility-tree step via ADB, explicitly “no screenshots needed”). Suggested architecture: Page/app state exposed as an accessibility tree or DOM snapshot → Jev Choice over the candidate interactive elements → execute the chosen action; fall back to a full vision-reasoning model only when Jev’s confidence is low. Example workflow: Mirrors the two community projects above directly — this is not a TypeSafe-documented use case, it’s something builders assembled because the primitive fit. Limitations: Jev is text-only — it can judge a textual/structural representation of a page (accessibility tree, DOM, extracted labels), not raw pixels. No native browser-control layer exists; you still need your own browser-automation tool underneath (e.g. the kind covered in this site’s own browser-automation coverage).

Coding — [community]

Problem: Reviewing diffs, deciding what’s safe to auto-merge, and routing coding subtasks to the cheapest adequate model are classification problems wearing a coding costume. Why JEV fits: Same community cluster as “AI engineering agents” above — jev-review (staged code review with a local dashboard) and jev-router (routes Claude Code to the cheapest suitable model) are both built specifically for this. Suggested architecture: Diff/PR → Jev Score (risk) + Choice (which reviewer path: auto-merge / lint-only / human review) → gate the merge on the result. Example workflow: Same compaction idea as fast-jev-compaction: instead of generating a prose summary of tool calls for a coding agent’s context window, score their relevance with Jev and keep only what’s load-bearing. Limitations: None of this is an official TypeSafe product; you’re adopting someone else’s glue code, and it needs the same review you’d give any third-party dependency touching your CI pipeline.

Long-running autonomous jobs — [composed]

Problem: The longer an autonomous agent runs unsupervised, the more it drifts — loses track of the original goal, repeats work, or keeps “confirming” things that don’t need reconfirming. Why JEV fits: foreman (the community agent-supervisor project cited above) and the arXiv pentest paper’s “agent pruning” and “confirmation loop” decision points are both direct answers to drift and redundant-checking, using fast bounded judgments instead of asking the expensive reasoning model to re-evaluate its own state. Suggested architecture: Agent loop → periodic Jev Noul (“is this action still aligned with the original goal?”) + Score (“how much new information did this step actually produce?”) → low-information or off-goal steps get pruned before they consume another full reasoning-model turn. Example workflow: A coding agent mid-task checks in with Jev every N tool calls rather than re-reasoning from scratch about whether it’s still on track. Limitations: Jev has no memory of its own, so “the original goal” has to be re-supplied as state on every check — the long-running context management is entirely the host agent’s responsibility, not something Jev provides.

Competitive context

None of the following compete with Jev directly — they’re orchestration layers, and Jev is a primitive you’d call from inside one. Worth naming anyway, because “should I use JEV instead of X” is the wrong question for every X below; “could JEV make X’s decisions cheaper” is the right one. For a full head-to-head of the two self-hosted options named first below, see our separate OpenClaw vs Hermes Agent comparison; if you’re instead weighing a hosted, consumer-facing “always-on” agent rather than something you self-host or orchestrate yourself, that’s a different category covered in Meta Muse vs OpenAI Dots vs Grok Bot.

  • Hermes Agent — open-source (MIT), built by Nous Research, released February 2026. Runs on your own server, keeps a persistent three-layer memory, builds its own skills over time, and reaches you over Telegram/Discord/Slack/desktop. Owns everything Jev doesn’t: the loop, memory, and tool orchestration. You’d embed Jev inside a Hermes skill for a bounded decision, not replace Hermes with it.
  • OpenClaw — open-source (MIT), self-hosted, local-first agent runtime created by Peter Steinberger (PSPDFKit founder), now stewarded by the OpenClaw Foundation. Sandboxed skill execution, persistent memory, entirely on your own hardware. Same relationship to Jev as Hermes: orchestration layer that could call Jev for a narrow judgment, never a substitute for it.
  • Claude Code — the coding agent used to research and draft this article. A full agent harness with its own tool-use loop, memory, and MCP support; several of the community projects above (jev-router, fast-jev-compaction, jev-mcp) exist specifically to plug Jev into it.
  • OpenAI’s agent tooling (AgentKit / Agents SDK) — OpenAI’s current recommended code-first framework for building agents (Agents SDK, GA since March 2026, successor to Swarm), bundled with the Responses API and ChatKit. Same category as LangGraph/CrewAI below: it owns the agent loop, tool calling, and handoffs. A Choice/Score call to Jev is a plausible node inside an Agents SDK workflow, not a replacement for it.
  • n8n — low-code automation with native MCP support and 1,000+ integrations. The natural home for the workflow automation use case above: Jev as one HTTP node in an otherwise-visual pipeline.
  • LangGraph — graph-based, stateful agent orchestration, the common choice for complex branching workflows with human-approval checkpoints. Jev is a plausible node at a branch point; LangGraph still owns the graph, the state, and the checkpointing.
  • CrewAI — role-based multi-agent orchestration, generally the faster path to a simple team of agents. Same relationship as the others.

When I would use JEV

Where it’s an excellent choice: any point in a system you already control where you’re making the same kind of bounded, repeated, semantic decision at volume — routing, triage, scoring, extraction, a guardrail check, or a confidence-gated branch — and you’d otherwise be paying full generative-model cost and latency, or hand-writing brittle regex/rules, to get there. The strongest evidence for this in this guide isn’t TypeSafe’s own marketing, it’s the sheer number of independent community projects (coding routers, code review, browser automation on accessibility trees, agent supervisors) that converged on the same pattern without being told to.

Where another architecture is better: anything open-ended — chat, code generation, multi-step reasoning, planning. Anything that needs memory, tool orchestration, or a UI, which is to say an actual agent — reach for Hermes, OpenClaw, Claude Code, an Agents SDK build, LangGraph, or CrewAI, and consider calling Jev from one of those for the narrow decisions inside it. And anything that must run fully air-gapped or self-hosted today — Jev simply can’t, full stop.

Enterprise deployment considerations: the ZDR-on-request-plus-legal-docs story may satisfy some procurement processes and not others; there’s no public SOC 2/ISO/HIPAA certification to point to as of this research, so budget time for a direct conversation with TypeSafe’s sales team rather than assuming self-serve compliance. See enterprise AI budget planning for the broader framing of vendor risk vs. token cost.

Maturity risks: a seed-stage company (closed its round in September 2026), a product still in early access, rate limits explicitly described as still being tuned, and model aliases that can shift behavior under you if you don’t pin a version. None of this is unusual for a six-month-old product category — but it’s a different risk profile than adopting an established open-source framework with 95K+ or 340K+ GitHub stars (Hermes, OpenClaw respectively).

Operational complexity: low per-call — it really is “make an API call, read a probability back.” The complexity that remains lives entirely in your own confidence-threshold policy: what counts as “high enough to auto-act,” what triggers a human, and how you re-validate that policy as the model version changes. That’s exactly what the author’s own small pilot surfaced in practice — not the model being wrong, but a downstream bug (a quarantine rule that had been silently discarding six of nine nights of output) that the pilot’s disagreement cases happened to expose. On a 40-event sample, every answer at ≥0.9 confidence agreed with the deterministic reference map (14/14); every disagreement was at ≤0.51 confidence, and half of those turned out to be errors in the reference map, not the model. That’s a small, self-reported pilot, not a TypeSafe benchmark — but it’s the one number in this guide nobody else can cite, because it’s the author’s own.

Frequently Asked Questions

What is JEV in AI agents?

JEV (properly “Jev”) is TypeSafe AI’s “System One model” — a non-generative model that turns text/JSON input and a set of typed questions into typed answers with calibrated probabilities, for use inside software and agents, not as a standalone agent itself.

Is JEV the same as Jev AI (jev-ai.org)?

No. Jev AI is an independent community app for sharing Jev “playbooks”; its own README states it is not the official product site for the underlying Jev model. The official product is TypeSafe’s Jev at typesafe.ai / docs.typesafe.ai.

Can you self-host Jev?

No. TypeSafe’s Jev is API-only with no downloadable weights or on-prem build documented anywhere. (Don’t confuse it with the unrelated, genuinely self-hostable open-source model AgentJev-0.6B, which benchmarks against Jev but isn’t Jev.)

Does TypeSafe's Jev have an official MCP server?

Not as of this research. Several third-party/community MCP servers exist (jev-mcp, typesafe-mcp, decisions-judge-mcp, jev-shield) that bridge Jev’s API into MCP clients like Claude Code and Cursor.

How much does Jev cost?

$0.042 per million input tokens ($42 per billion); output tokens are free. No self-serve enterprise pricing tier is published — enterprise customers are directed to contact sales.

Is Jev an agent framework like LangGraph or CrewAI?

No. It has no agent loop, no built-in memory, and no native tool calling. It’s a decision primitive you’d call from inside a framework like LangGraph, CrewAI, Hermes, OpenClaw, or an Agents SDK build, not a replacement for any of them.

How does Jev handle uncertain answers?

It returns a calibrated probability/confidence with every answer, and TypeSafe recommends a three-tier policy: act automatically above a high threshold, confirm or flag for review in a medium band, and escalate to a human or fallback system below a low threshold — with the threshold itself scaled to how costly a wrong decision would be.

What are Jev's main limitations today?

Text-only input (no image/audio/video), no memory, no self-hosting, no official MCP server, model aliases that can drift behavior without a code change, no published compliance certifications, and rate limits still described as actively changing.
