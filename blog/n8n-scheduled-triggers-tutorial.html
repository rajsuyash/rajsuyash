n8n Schedule Trigger: Cron, Interval and Timezone Setup

The N8N Schedule Trigger runs your workflows automatically at any time you choose. This tutorial covers trigger rules, cron expressions, where the timezone really comes from, missed runs, and six example schedules.

Short answer: To run an n8n workflow on a schedule, add a Schedule Trigger node, add a Trigger Rule (seconds, minutes, hours, days, weeks, months or Custom Cron), then save and publish the workflow. The schedule runs in the workflow's timezone setting, or the instance default, GENERIC_TIMEZONE, which is America/New_York. The node has no timezone field of its own.

Updated October 27, 2026. I checked this page against the n8n docs and the Schedule Trigger source code for n8n 2.45.4, the stable release that day. I did not run an n8n instance for this update, so everything below is documented behavior or read from the node source, not something I timed on a live server. Most n8n workflows are reactive: a webhook fires, a form is submitted, a record changes. A lot of useful automation is time-based instead: pull a report every morning, send a reminder every Friday, sync data every hour, clean up old records on Sunday night. That is the job of the Schedule Trigger. If you are new to n8n, start with How to Build Your First N8N Workflow and come back when you are ready to put a workflow on a timer.

Official docs vs this guide. The node reference lives with n8n: Schedule Trigger documentation, plus its common issues page. They list every parameter and track each release. This is not an n8n site and does not replace them. What you get here: the cron syntax field by field, where the timezone really comes from, what changed in how missed runs and short intervals behave, and six example schedules.

What the N8N Schedule Trigger Does

The Schedule Trigger sits at the start of a workflow and fires on the clock instead of on an external event. The node's own notice says the workflow runs on the schedule you define once you publish it. Publishing is the step people forget: the n8n docs say that if a workflow uses the Schedule Trigger, you must save and publish it.

Trigger Intervals and Trigger Rules

The node does not have "interval", "fixed time" and "cron" modes. It has a list of Trigger Rules, and each rule has a Trigger Interval of Seconds, Minutes, Hours, Days, Weeks, Months or Custom (Cron). The other fields depend on the interval you pick. This table is built from the node source and the docs.

Trigger Interval Fields Example from the docs
Seconds Seconds Between Triggers 30: every 30 seconds
Minutes Minutes Between Triggers 5: every 5 minutes
Hours Hours Between Triggers, Trigger at Minute (0-59) 6 and 30: every six hours at 30 minutes past
Days Days Between Triggers, Trigger at Hour, Trigger at Minute 2, 9am, 15: every two days at 9:15am
Weeks Weeks Between Triggers, Trigger on Weekdays, Trigger at Hour, Trigger at Minute 2, Monday, 3pm, 30: every two weeks on Monday at 3:30pm
Months Months Between Triggers, Trigger at Day of Month (1-31), Trigger at Hour, Trigger at Minute 3, 28, 9am, 0: each quarter on the 28th at 9:00am
Custom (Cron) Expression 0 9 * * 1-5: 9:00am Monday to Friday

Three behaviors from the docs that trip people up:

  • One node, several schedules. A Schedule Trigger can hold multiple Trigger Rules and runs on each of them. An earlier version of this page told you to split a workflow in two to get two schedules. You do not need to.
  • Short intervals are measured from publication. From n8n 2.45.0, by default, the Seconds and Minutes intervals run at uniform intervals counted from when you published the workflow, not on clock boundaries. Custom (Cron) keeps its clock timing. If you want a run at :00, :15, :30 and :45 of every hour, use the cron expression */15 * * * *, not "every 15 minutes".
  • Changing a schedule needs a republish. A new interval, or a changed variable used in the schedule, only takes effect after you unpublish and publish again, and the new schedule counts from that moment. The docs give the example of an hourly schedule changed to every two hours at 11:30: the next run is 13:30. Variables in a schedule are evaluated only at publish time.

In the Months interval, a day that does not exist in a month means no run: the docs note that a Day of Month of 30 will not trigger in February.

Custom Cron Expressions

Cron gives you what the dropdowns cannot, such as every hour from 9:00 to 17:00 or the first day of each quarter. The format is:

(second) minute hour day-of-month month day-of-week

The leading seconds field is optional: the n8n docs say the node runs even if you do not set it, and show */10 * * * * * for every 10 seconds. Day of week runs Sunday to Saturday. Each field takes a number, a wildcard (*), a range (1-5), a list (1,3,5) or a step (*/4).

Cron Expression When It Runs
0 9 * * 1-5 9:00 AM every weekday (Mon-Fri)
0 */4 * * * Every 4 hours (midnight, 4 AM, 8 AM, noon...)
*/15 * * * * Every 15 minutes, on the quarter hour
0 9-17 * * * Every hour from 9:00 AM to 5:00 PM, every day
0 9,13,17 * * 1-5 9 AM, 1 PM and 5 PM on weekdays
0 18 * * 5 6:00 PM every Friday
30 8 1 * * 8:30 AM on the 1st of every month
0 0 1 1,4,7,10 * Midnight on the 1st of January, April, July and October

If the node reports "Invalid cron expression", check the syntax against the examples above and paste the expression, without the seconds field, into crontab.guru. The node also validates the expression when you run it manually.

Timezone Configuration

This is the part the page used to get wrong. I read the node's parameter list in the n8n source: it has Trigger Rules and the missed-execution options, and no Timezone field. The node asks n8n for the workflow timezone when it starts, and n8n takes that from these places, per the docs:

  • Self-hosted, whole instance: the GENERIC_TIMEZONE environment variable. The n8n docs list its default as America/New_York, not the server's clock.
  • n8n Cloud, whole instance: the instance timezone setting described in the Cloud docs.
  • One workflow: open the workflow, then Workflow menu, Settings, Timezone, then Save.

Use IANA names such as Europe/Paris, America/New_York, Asia/Kolkata or Australia/Sydney. Here is what leaving the default in place does to a rule meant for 9:00 in Paris. I computed this with Python's zoneinfo on October 27, 2026, for a rule that fires at 09:00 America/New_York:

Date 09:00 New York is Paris Kolkata
2026-10-20 13:00 UTC 15:00 18:30
2026-10-28 13:00 UTC 14:00 18:30
2026-11-03 14:00 UTC 15:00 19:30

Paris is six hours ahead of New York on October 20, five hours ahead on October 28 (Europe has left summer time, the US has not yet), and six again on November 3. A job that looks right in one week lands an hour off in the next, which is why a workflow that matters should have its timezone set on purpose. To see which zone a run used, read the output item: the trigger emits a Timezone field (for example Europe/Paris (UTC+01:00)), plus readable date, time, day of week and the hour and minute, all in that zone.

How to Test Scheduled Workflows

You do not have to wait for the next run. The node's own notice says: for testing, you can trigger it manually by going back to the canvas and executing the workflow. A manual run emits a single item stamped with the current time in the workflow timezone, and all downstream nodes run with real data, so you see the actual API responses, database writes and Slack messages.

A manual run does not start the schedule. Once the logic passes, save and publish the workflow. Until you publish, the schedule does not fire.

Hosting Requirements and Missed Runs

Scheduled triggers only fire while the n8n process is running. If n8n is on a laptop that sleeps, the runs that fall during the sleep do not happen. Newer versions can make up for some of that, with limits:

  • From n8n 2.36 the node has an If Execution Is Missed option on its Settings tab: Don't Run Missed Executions (the default), Run the Most Recent Missed Execution, or Run the Most Recent Missed Execution Per Rule. It also has a Missed Execution Grace Period, where 0 means the instance setting N8N_SCHEDULER_MISFIRE_GRACE, 60 seconds by default.
  • These options appear on Schedule Trigger nodes added from 2.36 on, and only work on the durable scheduler, which is on by default from n8n 2.45.0. With N8N_SCHEDULER_ENABLED=false, n8n uses the in-memory scheduler, which never runs missed executions.
  • The catch-up is one run for the most recent missed time, not one run per missed slot.

For schedules that matter, host n8n on infrastructure that stays online:

  • n8n Cloud: managed, always on. Set the instance timezone as described in the Cloud docs.
  • A VPS (DigitalOcean, Hetzner, Linode): self-host n8n with Docker. My self-hosting guide covers the setup; check current provider prices yourself, because they change.
  • Railway or Render: managed container hosting with a persistent process.

For the wider picture of what n8n work involves, see the n8n automation page. If you self-host n8n for other people's businesses, read what the Sustainable Use License allows consultants to do first.

Six Example Schedules

These are sketches of common scheduled workflows, not tested builds. I have not run them on a live instance for this update, and the filters and field names will differ in your accounts.

1. Daily Sales Report to Slack

Schedule: weekdays at 8:00 AM (0 8 * * 1-5)

Workflow: Schedule Trigger → HTTP Request (yesterday's orders from the Shopify or WooCommerce API) → Code node (revenue, order count, average order value) → Slack node (post the summary to a sales channel). Use the HTTP Request node for any API without a dedicated node.

2. Weekly Lead Follow-Up Reminder

Schedule: Mondays at 9:00 AM (0 9 * * 1)

Workflow: Schedule Trigger → HubSpot node (contacts with status "contacted" and no activity for 7 days) → IF node (no response) → Gmail node (follow-up email) → HubSpot node (update the last activity date). The Gmail integration guide covers the OAuth2 setup the email step needs.

3. Low-Stock Alert

Schedule: daily at 7:00 AM (0 7 * * *)

Workflow: Schedule Trigger → Shopify node (product variants) → IF node (inventory below your threshold) → Slack node (list of low-stock SKUs) → Google Sheets node (append to a log).

4. Overdue Invoice Reminders

Schedule: weekdays at 10:00 AM (0 10 * * 1-5)

Workflow: Schedule Trigger → Xero or QuickBooks node (overdue invoices) → IF node (more than 7 days past due) → Gmail node (reminder to the client) → accounting node (note on the invoice). Send reminders to a test address until you trust the filter.

5. Hourly Data Sync

Schedule: every hour on the hour (0 * * * *)

Workflow: Schedule Trigger → HTTP Request (records changed since the last run) → IF node (only records with changes) → Airtable, Google Sheets or CRM node (write the updates). Polling keeps two systems within an hour of each other. See the Airtable integration guide for the write side.

6. Weekly Database Cleanup

Schedule: Sundays at 11:00 PM (0 23 * * 0)

Workflow: Schedule Trigger → database node (archived records older than 90 days) → IF node (confirm they qualify) → database node (delete) → Slack node (record count removed). Deletion cannot be undone, so run it for a few weeks with the delete step switched off and compare the counts first.

Common Mistakes with Scheduled Triggers

  • Not publishing the workflow. The docs say you must save and publish. A workflow that was only saved, or that you only ran manually, has no schedule.
  • Assuming the node has its own timezone. It does not. Set the workflow timezone, or GENERIC_TIMEZONE for the instance, and confirm with the Timezone field in the output.
  • Expecting "every 15 minutes" to land on the quarter hour. On n8n 2.45.0 and later, Minutes and Seconds intervals count from publication. Use cron for clock-aligned runs.
  • Editing a schedule without republishing. The change, or a changed variable, does not apply until you unpublish and publish again.
  • Running n8n on a machine that sleeps. Missed runs are skipped by default, and the catch-up options need a recent version and the durable scheduler.
  • No error notification. Scheduled workflows run unattended. Create a workflow that starts with the Error Trigger node, then pick it under Settings, Error workflow in each scheduled workflow. The docs note an error workflow does not need to be published, and that it only runs when an automatic execution fails, not when you run a workflow manually. More in the n8n error handling guide.
  • Relying on execution history as your log. By default n8n prunes executions: EXECUTIONS_DATA_PRUNE is on, EXECUTIONS_DATA_MAX_AGE is 336 hours (14 days) and EXECUTIONS_DATA_PRUNE_MAX_COUNT is 10,000 (docs checked October 27, 2026). Write a summary row to Google Sheets or Airtable if you need a longer record.

Combining Schedule Trigger with Other Nodes

Schedule + Wait node: the Wait node pauses the execution, stores its data in the database, and resumes after a time interval, at a specified time, on a webhook call or on a form submission. Useful for "notify now, follow up in an hour".

Schedule + Loop Over Items (Split in Batches): most n8n nodes already process a whole list of items, so you often do not need it. The n8n docs point to batching API calls to avoid rate limits as one case where it helps; the retries and rate limits guide goes further.

Several schedules, one workflow: add more Trigger Rules to the same Schedule Trigger. If two schedules need different logic, split them into two workflows that share steps through a sub-workflow call.

Frequently Asked Questions

Where are the official n8n Schedule Trigger docs?

On docs.n8n.io, under Integrations, Built-in nodes, Core nodes, Schedule Trigger, with a separate Common issues page. The reference is the authority on parameters and tracks each release. It is written as a reference, not a tutorial, which is the gap this guide fills.

How do I run an n8n workflow on a schedule?

Add a Schedule Trigger node, add a Trigger Rule (seconds, minutes, hours, days, weeks, months or Custom Cron), then save and publish the workflow. The n8n docs say you must publish a workflow that starts with the Schedule Trigger, otherwise the schedule does not run. One node can hold several rules, and each rule fires on its own.

How do I set the timezone for an n8n Schedule Trigger?

The node has no timezone field. n8n runs the schedule in the workflow timezone: open the workflow, then Workflow menu, Settings, Timezone. The instance-wide default comes from the GENERIC_TIMEZONE environment variable on self-hosted n8n (its default is America/New_York) or from the instance timezone setting on n8n Cloud. Use an IANA name such as Europe/Paris or Asia/Kolkata.

How do I write a cron expression in n8n?

Pick Custom (Cron) as the Trigger Interval and enter the expression: minute, hour, day of month, month, day of week. n8n also accepts an optional leading seconds field, so */10 * * * * * runs every 10 seconds. Examples: 0 9 * * 1-5 is 9:00 AM Monday to Friday, 0 */4 * * * is every 4 hours, 30 8 1 * * is 8:30 AM on the 1st of each month. The n8n docs suggest checking an expression on crontab guru after removing the seconds field.

Will n8n scheduled workflows run if n8n is down or my computer is off?

No. A schedule only fires while the n8n process is running, so a laptop that sleeps misses its runs. From n8n 2.36 the Schedule Trigger has an If Execution Is Missed setting with three choices: do not run missed executions (the default), run the most recent missed execution, or run the most recent missed execution per rule. It applies to nodes added from 2.36 and only on the durable scheduler, which is on by default from n8n 2.45.0.

How do I test a scheduled n8n workflow without waiting for the next run?

Go back to the canvas and execute the workflow manually. The Schedule Trigger node says so itself: for testing, you can trigger it manually. A manual run emits one item with the current time, so you can check the Timezone field and test every downstream node. Publish the workflow afterwards, because a manual run does not start the schedule.
